# Stabilization 0.1 성능 측정 결과

기준 앱: `8341e9ac09f2f791a28311ce4e97d577536c37ac`. 수정 앱/측정 ref: `3b4dac3f7dbd02a85fe3655602e92f91f667eff0` (앱 최적화 `a127f92` 포함).

Linux, Node 24.19.0/npm 11.9.0, Chromium **154.0.8037.57**, viewport 1280×900, CPU throttling 없음.
같은 환경에서 순차 실행했고 각 버전 3라운드 × 4개 악보 크기를 측정했습니다.
아래 중앙값은 라운드의 중앙값을 다시 평균내지 않고 전체 원시 샘플을 모아 계산합니다.
초기/전체 SVG는 12개 샘플, 각 업데이트는 36개 샘플입니다. 단위는 별도 표시가 없으면 ms입니다.
네트워크 다운로드와 최초 폰트 준비는 제외하며, 동기 업데이트는 React flush + SVG + 강제 레이아웃까지입니다.
resize에는 2 RAF의 대기/ResizeObserver가 포함되므로 다른 동기 업데이트와 직접 비교하지 않습니다.
프레임 지연은 독립적인 연속 RAF의 인접 타임스탬프로 측정했으며 resize 대기 두 프레임을 합산하지 않습니다.

작업 후는 각 시나리오 12회, 반복 작업은 각 시나리오 4회를 두 번 다시 마운트한 값입니다.
캐시와 이벤트별 DOM 참조를 유지하므로 수정 버전의 heap이 소폭 증가할 수 있습니다.
반복 작업 1→2에서 수십 KiB의 증가도 관찰되었습니다. 짧은 재마운트만으로 워밍업/캐시와 누수를 구분할 수 없으므로 장기 누수 부재를 주장하지 않습니다.
브라우저 전체 RSS·네이티브 SVG 메모리는 측정하지 않았습니다. 폰트/라이브러리 모듈 캐시 때문에 unmount 후 heap이 시작값으로 돌아오지는 않습니다.

## 해석과 남은 비용

64마디에서 음높이 수정은 64.90 → 2.30ms(약 96.5% 감소), 커서는 61.15 → 0.40ms(약 99.3% 감소)였습니다.
반면 초기 렌더는 78.50 → 90.60ms, 전역 조표 변경은 69.25 → 83.35ms,
박자 변경은 65.15 → 70.85ms, resize는 68.40 → 83.40ms로 커졌습니다.
전체 재배치의 비용과 캐시 관리 비용이 남으며, 모든 동작을 빠르게 했다고 주장하지 않습니다.
긴 작업 수는 84 → 36으로 줄었지만 64마디 최대 RAF 간격 중앙값은 100.10 → 133.30ms로 악화됐습니다.

반복 빈도가 높은 국소 편집의 큰 이득 때문에 최적화를 유지했습니다. 전역 설정/재배치와 초기 렌더 개선은
별도 후속 최적화 대상으로 남깁니다. 단순 번들 분할은 전체 다운로드량을 줄이지 않고 악보 표시에도
VexFlow/폰트가 바로 필요하므로, 이번에는 경고 억제나 확인되지 않은 분할을 적용하지 않았습니다.
